# Enrollment transaction codec prerequisite

`verifyEnrollmentTransaction` checks bytes against supplied public expectations.
It is deliberately disconnected from the hook, CLI, browser, state store and
runtime entry points. It makes no network requests and loads no identity/config.
It is not a completed enrollment or a protection-readiness check.

The expectations must have exactly the documented fields: target blockchain RID,
transaction RID, owner account ID, descriptor ID, session signer, agent public
key, organization, agent name, purpose, risk, policy name, and explicit Merkle
version (1 or 2). Hashes/IDs are lowercase 32-byte hex and public keys are real
compressed secp256k1 points. Labels are trimmed, nonempty and bounded. Accessor
fields, unknown fields and coercion are refused. The caller must independently
derive owner/descriptor authorization, chain routing and policy expectations;
this module does not establish that supplied expectations are trustworthy.

Only the demonstrated standard FT-login transaction is supported:

1. `ft4.ft_auth(ownerAccountId, descriptorId)`
2. `org_register_agent(agentPublicKey, organization, agentName, purpose, risk)`
3. `ft4.ft_auth(the same ownerAccountId, the same descriptorId)`
4. `org_assign_agent_policy(the same agentPublicKey, policyName)`
5. `nop(32-byte nonce)`

Every operation and argument must match exactly. There is precisely one expected
signer and one 64-byte signature. The canonical body RID must match the supplied
transaction RID and the signature must verify. A changed nonce is legitimate
only with its own valid signature and supplied matching RID. Extra FT4/product
operations, alternate authentication, multisig and assignment-only transactions
are refused. None is silently downgraded to an allowed template.

Input is copied before parsing, bounded to 65,536 bytes, and shared memory is
refused. An iterative DER preflight limits nesting to 24 constructed nodes and
total TLVs to 256, rejects indefinite/nonminimal/truncated lengths and trailing
bytes, and treats primitive payloads as opaque. Strict raw GTX arities precede
projection; canonical re-encoding must reproduce the full input. The separately
exported DER guard checks structure/resources only, never enrollment validity.
Failures return the same frozen `{valid:false}` with no raw diagnostics. Success
is a frozen public transaction RID, not receipt inclusion or policy authority.

The public fixture in `tests/fixtures/enrollment-ft4-2.1.0.json` was generated by
the actual FT4 2.1.0 builder and Postchain 2.1.2, with a fresh synthetic in-memory
key and synthetic owner/descriptor. No secret key is committed. To regenerate
into a **new** filename, provide a dependency project containing those exact
versions to `node scripts/generate-enrollment-fixture.mjs <dependency-root>
<new-output-file>`. The generator calls `build()` only and rejects network/client
access. Normal tests require only this repository's already-pinned Postchain
dependency and committed fixture, not FT4 or a sibling checkout.

Tests include genuinely re-signed wrong templates, positive fresh-nonce control,
malformed schemas/DER, cardinality and signature failures, bounded-parser edge
cases and the upstream version-sensitive `[[1]]` hash fixture. The enrollment
fixture itself has identical v1/v2 hashes; tests do not claim otherwise. Local
codec evidence does not prove positive live chain-version discovery.

Integration still needs independently verified expected values, bounded receipt
transport, trusted-node inclusion semantics, durable pre-broadcast transaction
acknowledgment and uncertain-outcome recovery, current policy/revision/hash and
enforcement readback, and pinned SDK action routing. Already-present agents need
current-state evidence without invented receipt fields or an extra transaction.
No live activation or few-second timing claim follows from this prerequisite.
